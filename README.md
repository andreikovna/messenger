# Чат с консультантом

Тестовое задание: мини-страница `/chat` со списком встреч и WebSocket-чатом.

## Стек

- Next.js (App Router)
- TypeScript
- TanStack Query
- Tailwind CSS

## Запуск

```bash
npm install
npm run ws    # терминал 1 — WebSocket echo-сервер на ws://localhost:8081
npm run dev   # терминал 2 — Next.js на http://localhost:3000
```

Страница чата: [http://localhost:3000/chat](http://localhost:3000/chat)  
Корень (`/`) редиректит на `/chat`.

## Функциональность

### Список встреч

- 5 встреч приходят с `GET /api/meetings` (мок-данные захардкожены в route handler)
- Список рендерится на сервере — виден в HTML при отключённом JS
- Кнопка «Обновить» перезапрашивает данные без перезагрузки страницы
- Клик по карточке открывает модалку редактирования (название, дата, статус) → `PATCH /api/meetings/:id`
- На мобилке список сворачивается до 2 карточек

### Чат

- Отправленное сообщение появляется в ленте сразу, до ответа сервера — статус «Отправляется»
- После подтверждения от сервера — «Доставлено», затем ответ консультанта
- Сообщения сгруппированы по дням с разделителем «Сегодня» / «Вчера» / датой
- Индикатор соединения в шапке и в чате: «Онлайн» / «Подключение...» / «Нет связи»
- При обрыве — красный баннер «Соединение потеряно»
- Неотправленные сообщения помечаются «Не отправлено» и не теряются
- После переподключения они уходят автоматически; есть и кнопка «Повторить» на случай, если сервер недоступен долго
- Переподключение автоматическое, без перезагрузки страницы

## Искусственные задержки (важно для демо)

В коде есть три таймаута, добавленных **специально** — все они помечены комментариями. Без них состояния меняются быстрее, чем их можно заметить, и работа оптимистичной отправки на UI не видна.

| Константа | Где | Зачем |
|-----------|-----|-------|
| `MIN_SENDING_VISIBLE_MS = 800` | `hooks/useChat.ts` | Держит статус «Отправляется» видимым. Echo-сервер отвечает за 300 мс, поэтому без задержки статус мелькает |
| `REPLY_AFTER_DELIVERED_MS = 350` | `hooks/useChat.ts` | Пауза между «Доставлено» и ответом консультанта, чтобы ACK успели заметить |
| `REFRESH_MIN_DELAY_MS = 800` | `components/MeetingsList.tsx` | Спиннер «Обновление...». Локальный мок отвечает мгновенно, и без задержки непонятно, что refetch произошёл |

Важно: **сеть не тормозим**. Сообщение уходит в сокет сразу, задерживается только смена статуса на экране. Задержка 300 мс и обрыв раз в 25–35 с в `server.js` — из условия задани.

## Как проверить обрыв связи и повтор отправки

Сервер сам рвёт соединение раз в 25–35 с, но окно, в которое сообщение может «не уехать», — меньше секунды, и переподключение почти сразу отправляет его повторно. Чтобы увидеть состояние «Не отправлено» и кнопку «Повторить» гарантированно:

1. Остановить ws-сервер (Ctrl+C в терминале с `npm run ws`)
2. Отправить сообщение — оно останется в статусе «Не отправлено» с кнопкой «Повторить»
3. Запустить `npm run ws` снова — сообщение уйдёт само, без нажатий и без перезагрузки страницы

## Архитектурные решения

### Граница Server / Client Components

| Слой | Файл | Роль |
|------|------|------|
| Server | `app/chat/page.tsx` | `prefetchQuery` + `HydrationBoundary` — начальные данные встреч попадают в HTML |
| Client | `components/MeetingsList.tsx` | `useQuery`, кнопка «Обновить», открытие модалки редактирования |
| Client | `components/MeetingModal.tsx` | `useMutation` — форма редактирования встречи |
| Client | `components/ChatShell.tsx` | Layout страницы чата; логика в `useChat` / `useWebSocket` |

**Почему так:** список встреч рендерится на сервере (SSR client-компонента с prefetched cache) — HTML виден даже при отключённом JS. Интерактив (обновление списка, редактирование, чат) живёт на клиенте.

`app/providers.tsx` — Client Component-обёртка с `QueryClientProvider`, подключена в `app/layout.tsx`, потому что TanStack Query требует React Context, а layout по умолчанию — Server Component.

### TanStack Query для SSR и мутаций

**Чтение (SSR + refetch):**

1. Server Component (`app/chat/page.tsx`) вызывает `prefetchQuery` с ключом `["meetings"]`
2. Состояние передаётся клиенту через `dehydrate` / `HydrationBoundary`
3. `MeetingsList` использует `useQuery` с тем же ключом — данные уже в кеше, loading-состояния нет
4. Кнопка «Обновить» вызывает `refetch()` — перезапрос `GET /api/meetings` без reload страницы

**Запись (редактирование встречи):**

1. Клик по `MeetingCard` открывает `MeetingModal` (portal в `document.body`)
2. `useMutation` вызывает `PATCH /api/meetings/[id]`
3. После успеха — `invalidateQueries({ queryKey: ["meetings"] })`, модалка закрывается
4. Мок-данные хранятся in-memory на сервере (`globalThis`); правки через PATCH сохраняются до перезапуска dev-сервера

### WebSocket и reconnect

Логика чата разложена по слоям, каждый занимается одним:

| Слой | Файл | Ответственность |
|------|------|-----------------|
| Транспорт | `hooks/useWebSocket.ts` | Соединение, reconnect (backoff 1s → 2s → 4s → max 10s), send/receive, статус |
| Протокол | `lib/chatWire.ts` | Формат `{id, text}`, сериализация и разбор входящих |
| Таймеры | `hooks/useTimers.ts` | Реестр отложенных задач по ключу «id сообщения + имя», отмена и очистка |
| Логика | `hooks/useChat.ts` | Статусы сообщений, оптимистичная отправка, ACK, очередь на переотправку |
| UI | `ChatShell` / `ChatWidget` / `MessageBubble` | Только отображение и события |

Echo-сервер: `server.js` (порт 8081, задержка 300 мс, обрыв каждые ~25–35 с). Статус соединения отображается в `Header` и `ChatWidget` через `ConnectionStatus`.

Отдельный `useTimers` появился потому, что искусственные задержки требуют управления жизненным циклом таймеров: их нужно гасить при обрыве, при повторной отправке и при размонтировании. Без выделения этой механики она расползалась по `useChat` и была самой запутанной частью кода.

**Как отличаем ACK от нового сообщения:** сервер — простой echo, поэтому клиент отправляет JSON `{id, text}` и хранит id в `pendingIds`. Вернувшееся сообщение со «своим» id считается подтверждением доставки, а не репликой консультанта; всё остальное добавляется в ленту как ответ.

**При обрыве:** сообщения в статусе `sending` переводятся в `failed`, отложенные таймеры доставки отменяются, показывается баннер. Если ACK успел прийти, но «Доставлено» ещё не отрисовалось, отменяется и запланированный ответ консультанта — иначе после переотправки echo продублировался бы.

**После reconnect:** на `onopen` все `failed`-сообщения уходят повторно с тем же id, поэтому в ленте не появляется дубль пользовательского пузыря — переиспользуется существующий.

### Декомпозиция UI

- `MeetingCard` — карточка встречи (статус, дата, клик → модалка)
- `MessageBubble` — пузырь сообщения со статусом доставки и кнопкой «Повторить»
- `Header` — шапка страницы с индикатором соединения
- `ConnectionStatus` — переиспользуемый индикатор состояния WebSocket

В интерфейсе нет декоративных кнопок-заглушек: любой видимый контрол что-то делает.

### Адаптив

- **Desktop (≥1280px):** две колонки — встречи слева (~320px), чат справа
- **Планшет (768–1279px):** две колонки, компактнее
- **Мобилка (<768px):** одна колонка, встречи сворачиваются с «Показать (ещё N …)» / «Свернуть»

## Структура проекта

```
app/
  page.tsx                    # редирект на /chat
  chat/page.tsx               # Server Component — точка входа
  api/meetings/
    route.ts                  # GET /api/meetings — мок-данные
    [id]/route.ts             # PATCH /api/meetings/:id — обновление встречи
  providers.tsx               # QueryClientProvider
components/
  MeetingsList.tsx            # Список встреч (Client)
  MeetingCard.tsx             # Карточка встречи
  MeetingModal.tsx            # Модалка редактирования (Client)
  ChatShell.tsx               # Layout страницы чата (Client)
  ChatWidget.tsx              # UI чата (Client)
  MessageBubble.tsx           # Пузырь сообщения
  Header.tsx                  # Шапка страницы
  ConnectionStatus.tsx        # Индикатор WebSocket-соединения
hooks/
  useWebSocket.ts             # Транспорт: соединение / reconnect / send / receive
  useTimers.ts                # Реестр отложенных задач с отменой
  useChat.ts                  # Логика чата: статусы / ACK / переотправка
lib/
  chatWire.ts                 # Формат сообщений в сокете {id, text}
  meetings.ts                 # Данные, fetch и update-функции
  types.ts                    # TypeScript-типы
server.js                     # Echo WebSocket сервер
```
